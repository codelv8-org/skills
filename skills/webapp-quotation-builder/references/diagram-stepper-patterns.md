# แผนภาพและ Stepper สำหรับสไลด์ข้อเสนอ

เลือกแผนภาพจากความสัมพันธ์ในขอบเขตและเงื่อนไขที่ลูกค้ายืนยัน

| คำถามลูกค้า | รูปแบบ |
|---|---|
| การพัฒนามีกี่ขั้นตอน | Stepper ใส่เลขลำดับ 2–5 ขั้น ใช้แนวตั้งเมื่อชื่อยาว |
| ใครทำอะไรต่อจากใคร | Flowchart แยกการกระทำและจุดตัดสินใจด้วยรูปทรง |
| ระบบเชื่อมต่ออะไร | แผนภาพสถาปัตยกรรมแสดงขอบเขตระบบและป้ายการเชื่อมต่อ |
| ส่งงานเมื่อใด | Timeline แสดงช่วงเวลาที่ตกลงแล้ว |
| จ่ายเงินงวดใดและเท่าไร | การ์ดงวดชำระและแถบสัดส่วนรวม 100% |
| ลูกค้าจะได้รับโมดูลใด | Grid จัดกลุ่มตามบทบาทเมื่อมีข้อมูล |
| การดูแลหลังส่งมอบมีอะไร | ตารางบริการที่รวม ไม่รวม และมีค่าใช้จ่าย |

## Stepper ขนาด 16:9

- วาง 3–5 ขั้นต่อแถวจากซ้ายไปขวา ใช้ `stepNumber` ต่อเนื่อง ป้าย `ขั้นที่ 1` และชื่อขั้นไม่เกิน 2 บรรทัดเมื่อทำได้
- วงกลม 0.50–0.56 in เส้นเชื่อมหนา 0.025–0.04 in อยู่ด้านหลังและผ่านจุดกึ่งกลาง ชื่อขั้น 18–20 pt ระยะเวลาหรือผลส่งมอบที่ตกลงแล้ว 15–17 pt
- แสดงสถานะเสร็จแล้วเมื่อมีข้อมูลจริง ชุดสำหรับแผนงานใช้ชื่อผลลัพธ์เช่น `ส่งมอบ` ใช้ความสูงและแนววางการ์ดเท่ากัน
- เกิน 5 ขั้นให้แบ่งหน้าและคงเลขต่อเนื่อง วางเกณฑ์ UAT/ตรวจรับในแถบแยก ขนาดอย่างน้อย 16 pt

## Flowchart และสถาปัตยกรรม

- ใช้สี่เหลี่ยมมุมมนสำหรับเริ่ม/จบ สี่เหลี่ยมสำหรับกิจกรรม เพชรสำหรับจุดตัดสินใจ ลูกศรทึบสำหรับการส่งต่องาน เส้นประสำหรับความสัมพันธ์เสริมพร้อมคำอธิบาย
- กำกับทางแยกเช่น `ผ่าน` และ `แก้ไข` ให้ทางหลักไปขวาและทางแก้ไขย้อนไปด้านล่างเมื่อทำได้ ใช้จุดหักมุมฉากและต่อที่ขอบกล่องโดยหลบข้อความ
- ใช้กระบวนการย่อประมาณ 5 จุดในสไลด์ทั่วไป แผนภาพเชิงเทคนิคควรใช้เมื่อยืนยันผู้ใช้งาน ระบบ ข้อมูล บริการภายนอก และการเชื่อมต่อที่อยู่ในขอบเขตแล้ว
- กำกับ `HTTPS`, `API` หรือ `ส่งแจ้งเตือน` ตามข้อเท็จจริง ระบุ `ต้องยืนยันการเชื่อมต่อ` เมื่อยังไม่ตกลง และแสดงข้อผูกพัน PDPA หรือการเข้ารหัสตามขอบเขตที่ยืนยัน
- ใช้ขอบทึบสำหรับงานที่รวม ขอบประสำหรับงานเสริม พร้อมป้ายข้อความ คงรูปทรงและเส้นเชื่อมให้แก้ไขได้ใน PPTX

## งวดชำระ

- ความกว้างของแถบเท่ากับสัดส่วนราคาของแต่ละงวด ระบุ `งวดที่ N` และ `NN%` รวม 100%
- การ์ดมีลำดับ เปอร์เซ็นต์ ยอด THB และเงื่อนไขการชำระ เมื่อเกิน 3 งวดให้แบ่งหน้า คงลำดับและแสดงยอดรวมซ้ำ
- เน้น `ยอดรวมโครงการ` พร้อมสถานะ VAT ตามที่ตกลง แสดง WHT เป็นหมายเหตุการรับชำระแยกจากยอดรวม

## ตรวจแผนภาพ

ตรวจลำดับและป้ายบนเส้นเทียบกับข้อมูลจริง ใช้ขนาด ช่องว่างและแนวการ์ดสม่ำเสมอ แสดงข้อความหรือเลขร่วมกับสี และตรวจว่าแยกผลส่งมอบ งานเสริม ข้อยกเว้น และเหตุที่เริ่มงวดชำระได้ชัดเจน

## ข้อมูลแผนภาพใน JSON

กำหนด `quote-data.json.presentation_diagrams` เมื่อโหนดและเส้นเชื่อมผ่านการยืนยันแล้ว สไลด์อยู่หลังขอบเขตงานและก่อน Stepper รองรับ 2–5 โหนดต่อแผนภาพ สูงสุด 2 แผนภาพ เชื่อมตามลำดับซ้ายไปขวาและย้อนกลับจากจุดตัดสินใจได้หนึ่งขั้นหนึ่งเส้น

```json
{
  "presentation_diagrams": [
    {
      "type": "flow",
      "title": "ขั้นตอนการยื่นคำขอ",
      "subtitle": "ลำดับที่ตกลงให้พัฒนา",
      "nodes": [
        {"id":"start","kind":"start","label":"ผู้ใช้ส่งคำขอ"},
        {"id":"review","kind":"process","label":"เจ้าหน้าที่ตรวจสอบ"},
        {"id":"approval","kind":"decision","label":"อนุมัติหรือไม่?"},
        {"id":"end","kind":"end","label":"แจ้งผลการพิจารณา"}
      ],
      "edges": [
        {"from":"start","to":"review"},
        {"from":"review","to":"approval"},
        {"from":"approval","to":"end","label":"อนุมัติ"},
        {"from":"approval","to":"review","label":"แก้ไข"}
      ],
      "note": "ตัวอย่างโครงสร้างข้อมูลเพื่ออธิบายรูปแบบ ไม่ใช่ขอบเขตที่ยืนยันของโครงการใด"
    }
  ]
}
```

สำหรับแผนภาพสถาปัตยกรรม ใช้ `type: "architecture"` และ `kind: "actor" | "system" | "data" | "external"` ใส่เส้นเชื่อมเฉพาะการเชื่อมต่อในขอบเขตและกำกับ `label` ตามข้อมูลที่ยืนยัน
