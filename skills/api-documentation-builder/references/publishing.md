# Publishing and QA

## Common document style
- Default language Thai; preserve exact approved identifiers, HTTP methods, SQL types, and technical terms in English. Follow requested language when specified. Use concise Thai prose and expanded definitions on first mention.
- Provide a title, system label, document type, version/revision, generated date, audience, classification, scope, source evidence IDs, verification status and known limitations. Omit actual staff names/contact details; use roles or teams. Label each hypothetical artifact TEMPLATE — NOT VERIFIED.
- Design for actual usage: A4 portrait for prose, landscape pages for wide tables only if necessary, repeating table headers, page numbers, section hierarchy, readable contrast. Break wide dictionaries into a short summary + field detail blocks; do not shrink Thai text to illegible sizes. PDF and Markdown must agree on field types, keys, routes, constraints and caveats. Use diagrams only when evidence supports edges; don't imply guessed dependencies.
- Markdown: UTF-8, one H1, clear sections, stable identifiers, tables with escaped pipes, fenced snippets, relative links and no secret-bearing links or images. No raw source copy, no hidden HTML comments with extra information. Treat Markdown as the human/agent-readable canonical narrative.
- PDF: use the available PDF skill and local rendering tools. Check every page visually and via text extraction; avoid raster-only output, external links to internal hosts, PDF attachments, hidden text, forms, scripts or active content. Metadata must contain only approved title/version/team role. Do not expose fonts as artifacts.
- Publish in a new directory containing only intended artifacts. Include `release-manifest.md`: files, scope, source IDs (safe relative names or opaque identifiers), dates/versions, verification coverage, omissions, privacy review status, unresolved issues. Use `verified`, `partial`, or `template` accurately. The scanner does not certify compliance.
- If output is large, split by approved schema or API domain, supply a Markdown index, and maintain one canonical record per object/operation. Don't silently truncate. Describe coverage in counts of structural objects, never actual records.
