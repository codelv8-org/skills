# OpenAPI, API data semantics and agent tools

## REST contract

- Preserve approved OpenAPI version; prefer 3.1 for new verified contracts. In 3.1 use JSON Schema null unions (`type: [string, 'null']` or an approved composition); 3.0 uses `nullable: true` with an explicit type. Quote status keys in YAML. Use `required` for object membership and distinguish from nullable. Path parameters must be required, and names match placeholders exactly. Query/header/cookie parameters follow approved definitions. Never invent default values or formats.
- Give each operation a unique stable `operationId`; use relative path templates only. Include requestBody content and response content/statuses where known. Empty responses must reflect confirmed behavior. Distinguish global vs operation security (`security: []` explicitly removes auth; do not use it when auth is unknown). Match security scheme references/scopes to declared components. Auth docs must not imply permissions that are not evidenced. Do not list a production URL. For documented auth endpoints use placeholder host and verified relative path only; if path not approved, omit the example.
- Validate locally; only `#/...` references, no external refs, no external schema IDs/dynamic refs, no examples from source. If a schema uses unsupported constructs, disclose limitations and use a standards validator offline. For 3.1 avoid changing dialect keywords automatically. Ensure `required`, examples, enum, type constraints, HTTP statuses, security and reference documentation agree. Use safe hypothetical example values for non-personal fields; omit examples that would require realistic personal identifiers. If contract is incomplete, mark narrative partial and withhold executable spec or produce separate template.
- For API Data Dictionary use JSON Pointer (e.g. `#/components/schemas/Department/properties/code`) or a stable request/response field path with operation ID + location + status/media type. Distinguish same field name across schemas. Describe type, format, required, nullable, constraints, meaning, unit, classification and evidence. For nested arrays, use a consistent path convention (`items[].code`). For composed schemas note inheritance/alternatives; do not flatten conflicting types incorrectly.

## API consumer guide

Explain intended audience, prerequisites, approved onboarding flow, auth scheme and scopes, base URL placeholder, quick start, verified request construction, pagination/filtering only when known, response/error handling, retries only for safe/confirmed idempotent operations, rate limits only when evidenced, versioning/deprecation, contact role and troubleshooting without logging payloads or secrets. No live execution. Examples use reserved `.invalid` host, placeholder tokens and approved non-personal structural values. Separate requirements from recommended patterns.

## Governance

Document verified scope/roles, classification, access and retention rules, audit logging, data minimization, transport, rate limits, versioning, incident contact role, and unknowns. Clearly label proposed controls. Do not claim HIPAA/PDPA or other legal compliance. Do not grant access or collect personal data. Include privacy boundary for both input and release.

## AI Agent / MCP integration

An API operation is not automatically a tool. Only owner-approved operations whose input/output contains no actual personal data or restricted values, with verified schema and access rules, may be proposed. Explicitly deny unrestricted search, identifiers that select patient records, clinical record access, credential retrieval, write/delete/admin operations and generic URL/SQL execution. Exclude even read endpoints if data boundary is unverified. Prefer narrowly scoped non-personal structural or approved aggregate operations (privacy review required; aggregate is not automatically anonymous). Never call or deploy the tools.

Use a neutral, machine-readable `tools.json` manifest (not a claim that it is an MCP server): `schema_version`, `status` (`draft_for_review`), `tools` array. Each item includes `name`, `description`, `operationId`, `method`, `path`, `inputSchema` (JSON Schema object with exact approved inputs; `additionalProperties: false` when compatible), `outputSchema` when verified, `required_scopes`, `classification`, `side_effects`, `approval_required`, and `evidence_id`. Do not loosen source constraints; omit tools when shape/scopes or risk unknown. Default no tools. No credentials or base URL beyond placeholder. Cross-check operations and schemas with OpenAPI. If user requests MCP-native format, clearly distinguish MCP tool declaration from an implementation; use `name`, `description`, `inputSchema`, optional `outputSchema` only when supported and confirmed, with policy annotations separately. Require application-side authorization, argument validation, response filtering, least privilege, timeouts, audit without sensitive content and human approval before integration. Prompts and tool descriptions are not enforcement.

`AGENTS.md` states approved documentation context, denied operations, tool-use policy, source limitations, human approval boundaries, and no actual data access. `llms.txt` is a concise index of safe relative Markdown docs and what each covers, not a security control or an access-grant mechanism. Never embed actual datasets.
